# OpenNebula 新手架構指南

你只需要知道一件事：**這是一個讓學校能透過網頁管理虛擬機的系統**。

以下用最白話的方式解釋每個元件。

---

## 整體架構圖

```
┌─────────────────────────────────────────────────────────┐
│                    你的瀏覽器                              │
│              (React 前端 - Sunstone)                      │
│                                                         │
│  點擊「建立 VM」→ 呼叫 API → 看到結果                      │
└────────────────────────┬────────────────────────────────┘
                         │ HTTP / WebSocket
                         ▼
┌─────────────────────────────────────────────────────────┐
│              FireEdge Server (中間人)                      │
│              Node.js + Express                           │
│                                                         │
│  職責：                                                   │
│  1. 提供前端網頁檔案                                       │
│  2. 轉發 API 請求到後端                                    │
│  3. 處理登入、檔案上傳、加密等                               │
└────────────────────────┬────────────────────────────────┘
                         │ XML-RPC
                         ▼
┌─────────────────────────────────────────────────────────┐
│              OpenNebula Daemon (oned)                     │
│              核心引擎 - C++ 寫的                           │
│                                                         │
│  職責：                                                   │
│  1. 真正管理 VM（建立、開機、關機、刪除）                     │
│  2. 管理 Host（實體伺服器）                                 │
│  3. 管理網路、儲存、使用者權限                               │
│  4. 排程決定 VM 要跑在哪台 Host 上                          │
└────────────────────────┬────────────────────────────────┘
                         │ 管理
                         ▼
┌─────────────────────────────────────────────────────────┐
│              實體伺服器 (Host)                              │
│              學校的 GPU 主機                               │
│                                                         │
│  跑著 KVM 虛擬化，上面有一堆 VM                             │
│  每台 VM 就是學生拿到的一台「虛擬電腦」                       │
└─────────────────────────────────────────────────────────┘
```

## 名詞解釋

### OpenNebula Daemon (oned)

**一句話：** 整個系統的大腦。

- 它是用 C++ 寫的後端程式，跑在伺服器上
- 所有「真正做事」的操作都是它完成的：建立 VM、分配 GPU、管理網路
- 它提供 XML-RPC 介面讓外部程式呼叫
- **你不需要直接碰它**，FireEdge 會幫你跟它溝通

類比：oned 就像餐廳的廚房，你不會自己進廚房炒菜，你透過服務生（FireEdge）點餐。

---

### FireEdge Express Server

**一句話：** 前端和後端之間的翻譯官。

- 它是用 Node.js + Express 寫的中間層
- 前端（瀏覽器）不能直接跟 oned 溝通，需要透過 FireEdge 轉發
- 它做三件事：
  1. 把前端的 JSON 請求翻譯成 oned 看得懂的 XML-RPC 格式
  2. 處理登入驗證（JWT Token）
  3. 做一些 oned 做不到的事（檔案上傳、加密、讀日誌）

類比：FireEdge 就像餐廳的服務生，接收你的點單，翻譯給廚房，再把做好的菜端給你。

---

### Sunstone

**一句話：** 你在瀏覽器看到的管理後台網頁。

- 就是那個有側邊欄（VMs、Templates、Hosts...）的網頁介面
- 用 React 寫的單頁應用 (SPA)
- 所有操作（建立 VM、查看狀態、管理使用者）都在這個網頁上完成

類比：Sunstone 就是餐廳的菜單和餐桌，你在這裡看菜單、點餐、吃飯。

---

### RTK Query

**一句話：** 前端呼叫 API 的工具。

- 全名 Redux Toolkit Query，是 React 生態中管理 API 呼叫的套件
- 它幫前端做三件事：
  1. 發送 HTTP 請求（GET/POST/PUT/DELETE）
  2. 快取 API 回傳的資料（避免重複請求）
  3. 自動管理載入狀態（loading/success/error）

```javascript
// 例：前端要取得 VM 列表
const { data, isLoading } = useGetVmsQuery();
// RTK Query 自動幫你：
// 1. 發 GET /api/vmpool/info
// 2. 等回應
// 3. 把資料存到 Redux store
// 4. 下次再呼叫時直接從快取拿（不重複請求）
```

類比：RTK Query 就像一個聰明的助手，你說「幫我查 VM 列表」，它會自動去問 API、記住答案、下次你再問就直接回答。

---

### Guacamole

**一句話：** 讓你在瀏覽器裡直接連到 VM 的工具。

- Apache Guacamole 是一個開源的遠端桌面閘道
- 它支援 VNC（看桌面）、SSH（命令列）、RDP（Windows 遠端桌面）
- 在 OpenNebula 裡，你點 VM 的「Console」按鈕，就會透過 Guacamole 用 WebSocket 連到 VM

```
「你的瀏覽器」 ←WebSocket→ 「FireEdge」 ←TCP→ 「guacd daemon」 ←VNC/SSH/RDP→ 「VM」
```

類比：Guacamole 就像一個遠端遙控器，讓你坐在自己電腦前就能操作遠方的虛擬機。

**GPU 算力平台中的角色：** 學生可以透過 Guacamole 的 SSH 功能，直接在網頁上開 Terminal 連到 GPU VM，不需要額外安裝 SSH 工具。

---

### XML-RPC

**一句話：** oned 聽得懂的語言。

- XML-RPC 是一種古老但穩定的遠端呼叫協議
- oned 只接受 XML-RPC 格式的請求
- FireEdge 會把你的 JSON 請求轉成 XML-RPC，再轉發給 oned

```
你發送：GET /api/vm/info/0 (JSON)
FireEdge 轉成：one.vm.info(session, 0) (XML-RPC)
oned 回傳：<VM><ID>0</ID>...</VM> (XML)
FireEdge 轉成：{ "VM": { "ID": "0", ... } } (JSON)
你收到：JSON
```

**你不需要關心 XML-RPC**，FireEdge 已經幫你處理了轉換。

---

### Socket.IO / WebSocket

**一句話：** 讓伺服器主動推訊息給你的技術。

- 一般 HTTP 是「你問、伺服器答」，每次都要你主動問
- WebSocket 是「建立連線後，伺服器可以主動推訊息給你」
- 用途：
  - **Hook 事件**：VM 狀態變了（開機→關機），伺服器主動通知你的瀏覽器更新
  - **Guacamole**：SSH/VNC 的即時雙向資料傳輸

類比：HTTP 像寄信（你寫一封、等回信），WebSocket 像打電話（雙方隨時可以說話）。

---

### KVM

**一句話：** 讓一台實體電腦變出很多台虛擬電腦的技術。

- KVM 是 Linux 內建的虛擬化引擎
- 學校的 GPU 伺服器上跑著 KVM
- OpenNebula 透過 KVM 建立和管理 VM

---

### GPU 分配方式（三種模式）

GPU 給 VM 用有三種模式，差別在於「一張卡怎麼分」：

#### 模式一：GPU Passthrough（整張卡直通）

**一句話：** 一張 GPU 只給一台 VM 用，獨佔，效能最好。

```
實體 GPU（RTX 4090）
    │
    └── 100% 給 VM-A（其他人完全碰不到）
```

- 好處：效能最強，跟直接裝在電腦上一樣
- 壞處：一張卡只能給一個人，GPU 少的話大家要排隊等
- 適用 GPU：所有 GPU 都支援
- **你們學校目前就是這個模式**

---

#### 模式二：vGPU（虛擬 GPU — 軟體輪流用）

**比喻：** 一間會議室大家**輪流**用，每人分到固定的桌子大小（顯存），但投影機（運算核心）要排隊共用。

```
實體 GPU
    │
    ├── vGPU-1 → VM-A（分到 8GB 顯存，輪到時用整張卡的運算力）
    ├── vGPU-2 → VM-B（分到 8GB 顯存，排隊等 A 用完）
    ├── vGPU-3 → VM-C（分到 8GB 顯存，排隊等 B 用完）
    └── vGPU-4 → 空的 → VIP 來了馬上拿
```

- 運作方式：多台 VM **輪流**使用 GPU 運算核心（時間分片）
- 顯存：每台 VM 分到固定大小，互不干擾
- 運算核心：大家共用，輪流跑，可能會互相影響速度
- 好處：切片數量多（可達 10+），彈性高，可隨時建立/移除
- 壞處：需要 **NVIDIA GRID 商業授權**（要付錢給 NVIDIA）
- 適用 GPU：資料中心等級（A100、H100、RTX A6000 等）

---

#### 模式三：MIG（Multi-Instance GPU — 硬體隔成小房間）

**比喻：** 用實體牆壁把一間大會議室**隔成幾間小會議室**，每間有自己的桌子、投影機、空調，互不干擾。

```
實體 GPU（A100 80GB）
    │
    ├── MIG 實例 1 → VM-A（專屬 10GB 顯存 + 專屬運算核心，完全獨立）
    ├── MIG 實例 2 → VM-B（專屬 10GB 顯存 + 專屬運算核心，完全獨立）
    ├── MIG 實例 3 → VM-C（專屬 10GB 顯存 + 專屬運算核心，完全獨立）
    └── ...最多 7 個實例
```

- 運作方式：GPU 在**硬體層級**被切成獨立的小 GPU
- 顯存：專屬，硬體隔離
- 運算核心：專屬，不會被別人影響
- 好處：效能穩定可預測，隔離最強，VIP 付大錢最適合這個
- 壞處：最多只能切 7 份，改大小要**停機重設**（不能動態調整）
- 適用 GPU：只有高階卡支援（A100、A30、H100、H200）

---

#### 三種模式比較表

```
                 Passthrough        vGPU              MIG
                 ──────────         ────              ───
分法             整張卡獨佔         軟體切片           硬體隔間
效能             最強               中等（輪流用）     強（專屬資源）
隔離             最強（獨佔）       中等（顯存隔離）   很強（硬體隔離）
最多幾人用一張卡  1 人              10+ 人             最多 7 人
能不能動態調整    不能              可以               不行（要停機）
需要額外授權      不用              要（NVIDIA GRID）  不一定
適合場景          重度運算           大量輕度使用者     VIP 穩定保障
```

---

#### 三種模式對「VIP 插隊」的影響

```
Passthrough：GPU 都被佔滿 → VIP 只能「排第一個等」→ 要等別人用完或被管理員踢掉
vGPU：       切片多 → 比較容易有空的切片 → VIP 通常能馬上拿到
MIG：        切片少但獨立 → 效能最穩定 → 適合給 VIP 預留專屬隔間
```

**不管哪種模式**，OpenNebula 都當作「PCI 設備」來管理，走同一套排程系統。差別只在 Passthrough 是「整張卡」，vGPU/MIG 是「切片」。

源碼驗證：`src/vmm_mad/remotes/kvm/vgpu` 這個腳本同時處理 legacy mdev（vGPU）和 NVIDIA creatable_vgpu_types（含 MIG-backed vGPU）兩種路徑。

---

### USER_PRIORITY（VIP 插隊機制）

**一句話：** 讓某些人的 VM 排隊時插到最前面。

- 每台 VM 可以設定一個數字，數字越大 = 越優先
- OpenNebula 的排程器每次跑的時候，會**先服務數字大的 VM**

```
普通學生 A → USER_PRIORITY = 0
普通學生 B → USER_PRIORITY = 0
普通學生 C → USER_PRIORITY = 0
VIP 學生   → USER_PRIORITY = 100

排隊順序：VIP → A → B → C（VIP 永遠排第一）
```

- 注意：這只影響「排隊順序」，不會把正在跑的 VM 踢掉
- 如果所有 GPU 都被佔著，VIP 還是要等有 GPU 釋放才輪到他
- 但只要有 GPU 空出來，VIP 一定是第一個拿到的

---

### Host

**一句話：** 跑 VM 的實體伺服器。

- 在你們學校的場景中，Host 就是那台有 GPU 的伺服器（10.1.1.79）
- 一台 Host 上可以跑多台 VM
- OpenNebula 管理多台 Host，決定新的 VM 要放在哪台 Host 上

---

### VM Template

**一句話：** 建立 VM 的「預設組合」。

- 就像便當店的菜單：A 套餐（Ubuntu + 4CPU + 16G RAM + 1 GPU）
- 學生不需要從零設定 VM，選一個 Template 就能一鍵建立
- GPU 算力平台的核心：準備好 GPU Template，學生點一下就有一台 GPU VM

---

## 資料流總結

```
後台人員點「建立 GPU VM」
    │
    ▼
React 前端呼叫 useInstantiateTemplateMutation({ id: 1, name: "我的GPU" })
    │
    ▼ HTTP PUT /api/template/instantiate/1
FireEdge 收到請求
    │
    ▼ 轉成 XML-RPC: one.template.instantiate(session, 1, "我的GPU", ...)
oned 收到指令
    │
    ├── 檢查權限：這個學生有沒有權限建 VM？
    ├── 檢查配額：這個學生還能建幾台？
    ├── 排程：選一台有空的 GPU Host
    ├── 建立 VM：在 Host 上透過 KVM 啟動虛擬機
    └── 分配 GPU：用 PCI Passthrough 把 GPU 直通給 VM
    │
    ▼ 回傳 VM ID: 123
FireEdge 轉成 JSON 回傳
    │
    ▼
前端顯示「VM 建立成功！ID: 123」
    │
    ▼ WebSocket Hook 事件推送
前端自動更新 VM 狀態：PENDING → RUNNING
    │
    ▼
學生看到 VM 的 IP，用 SSH 連線開始跑 GPU 運算
```
